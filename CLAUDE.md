# CleanerCMS — Shared Project Context

## What this is
A contract management platform for UK commercial cleaning companies.
The central operational and financial hub between HR, payroll, accounting,
and time-and-attendance systems.
Full specification: /docs/spec.md

## Two agents, one shared contract
- Backend agent owns: apps/api, packages/db
- Frontend agent owns: apps/web
- Shared contract: packages/domain (TypeScript types + API shapes)
  Backend writes here. Frontend imports from here. Neither invents types independently.

## CRITICAL DOMAIN CONCEPTS

### 1. Flexible organisational hierarchy
No fixed Client → Site → Contract tree.
OrganisationalHierarchyNode — self-referential tree with user-defined types.
Site is a specific node type. Access control propagates DOWN the tree.

### 2. Draft vs Live — on everything important
Contract, Budget, Workplan, ServicePlan, StoreItemPlan all have Draft and Live states.
NEVER mutate a Live record. Always create a new Draft.
A Contract has many ContractVersions — only one is Live at a time.
All plans and budgets belong to a ContractVersion, not a Contract.

### 3. Budget valuation — three methods
Every Budget has exactly ONE:
  fixed       — manually entered value
  percentage  — X% of a source budget (CANNOT chain: percentage of a percentage is forbidden)
  calculated  — sum of child budgets + expected costs of nested plans + optional profitMarginPercent

Three metrics on every Budget:
  budgeted = target (from valuation method)
  expected = forecast from Plans
  actual   = from approved operational data

### 4. Plan → Scheduled Deliverable pattern
  Workplan     → Timesheet      (weekly, auto-generated by cron)
  ServicePlan  → Service        (per frequency, auto-generated by cron)
  StoreItemPlan → StoreItemOrder (per frequency, auto-generated by cron)
Plans generate expected cost. Deliverables capture actual cost once approved.

### 5. Labour hierarchy — three distinct entities
  WorkplanShift  = template shift in a Workplan (role, hours, staff count)
  TimesheetShift = planned shift copied into a Timesheet at week start
  Shift          = actual clock-in/out record (from T&A or manual)

### 6. Store items have fulfilment options
  StoreItem = the product (what is needed)
  StoreItemFulfilmentOption = supplier + price (how it's fulfilled)
  Multiple fulfilment options per item.

### 7. The Job object
All ad-hoc unplanned work is a Job. Two costing modes:
  Absorb   — costs go to an existing budget
  Billable — auto-creates a new top-level Budget, picked up by next Billing Run

### 8. Services vs Jobs
  Service = scheduled instance from a ServicePlan (recurring external work)
  Job     = ad-hoc one-off work (internal or external)

### 9. Claims-based permissions — NOT role checks
NEVER: if (user.role === 'ContractManager')
ALWAYS: if (user.hasClaim('contracts:create'))
Roles are bundles of claims. UserRoleAssignment scopes a role to an org node.
Claims apply to that node AND ALL DESCENDANTS.

### 10. Rate resolution for labour costing
EmployeeContract.overrideRate → Payscale for Role
Use overrideRate if set, otherwise use Payscale.hourlyRate.

## Financial rules (both agents must understand these)

### Expected cost
Workplan:      SUM(WorkplanShifts: staffCount x plannedHours x resolvedRate)
ServicePlan:   estimatedCost x visitsPerPeriod
StoreItemPlan: quantity x unitCost x ordersPerPeriod
Calculated Budget: SUM(children budgeted) + SUM(plan expected costs) x (1 + margin%)

### Amortisation — dual view
Accrual:    monthly = fixedValue / amortisationMonths
Cash flow:  month 1 = fixedValue, all other months = 0

### Holiday — 4 methods per EmployeeContract
1. Pro Rata Fixed:   contractedWeeklyHours x holidayWeeks (default 5.6)
2. Timesheet Accrual: actualHours x 0.1207 (default 12.07%)
3. Annualised:       annualHours / 52 x holidayWeeks
4. Averaged:         avgWeeklyHours_last52Weeks x holidayWeeks

### Payroll attribution — 3 methods
1. Pro-rata by hours worked per site
2. Pro-rata by labour value per site
3. Even split across active EmployeeContracts

## Approval thresholds (hardcoded Sprint 1–3, configurable Sprint 4)
Timesheet:           auto-approve if actual hours within 10% of planned
Job:                 auto-approve if estimatedCost < £500
StoreItemOrder:      auto-approve if value < remaining budget
CreditNote:          requires approval if value > £1,000
ContractVersion:     requires approval if projected margin < 5%

## Audit logging
Every mutation writes to AuditLog: userId, entityType, entityId, action,
oldValue (JSON), newValue (JSON), timestamp (UTC).
AuditLog is IMMUTABLE — no update or delete endpoints.
